
# Section 4 — Deployment & Robustness

## 4.1 Deployment objective

The target platform is Jetson Orin Nano at 15 W with a required throughput of at least
15 FPS. This corresponds to a maximum sequential frame budget of 66.67 ms.

The benchmark numbers in this section are reported only for hardware actually tested.
No Jetson FPS, latency, memory, power, or thermal result is inferred from the MacBook
Air M2 measurements.

## 4.3 Jetson deployment expectation

The intended deployment boundary is the exported ONNX model.

On the target:

```text
camera
 -> preprocessing
 -> TensorRT FP16/INT8
 -> detection/geometry
 -> pose
 -> SOP checks
 -> temporal stability
 -> structured assessment
```

TensorRT should be evaluated directly on the Jetson because engine building and runtime
performance are target-GPU dependent. The acceptance criterion remains p95 end-to-end
latency <= 66.67 ms at the required operating point.

This is an engineering expectation and deployment plan, not a benchmark result.

## 4.4 Quantisation

INT8 is treated as a post-training static quantisation experiment.

Calibration uses representative project images and evaluation uses the same held-out
test split for FP32 and INT8.

The decision criterion is geometry preservation first. A small latency improvement is
not sufficient justification for INT8 if segmentation/localisation errors propagate into
the pose estimate.

## 4.5 Failure behaviour

Section 2 already rejects the current real-image pose because the reprojection RMS is
28.40 px against a 3 px quality gate. The deployment layer preserves this conservative
behaviour.

A failed perception stage produces an explicit status instead of a synthetic pose:

```json
{
  "status": "POSE_UNRELIABLE",
  "failure": {
    "retryable": true,
    "safe_action": "MANUAL_INSPECTION"
  }
}
```

This allows downstream robotics software to distinguish:

- valid assessment;
- perception uncertainty;
- temporal instability;
- invalid input;
- inference failure.

A downstream consumer should never infer success from missing fields.

## 4.6 Temporal information

Because the pallet is stationary, consecutive frames provide redundant observations.

A five-frame window is used to:

1. reject isolated invalid observations;
2. median-filter x/y;
3. robustly aggregate orientation;
4. quantify temporal jitter;
5. reject windows that exceed the position/orientation stability thresholds.

This is intentionally simpler than adding a tracking framework or Kalman filter.

## 4.7 What remains unvalidated

The following require physical Jetson hardware:

- TensorRT FP16 latency;
- TensorRT INT8 latency;
- sustained FPS at 15 W;
- Jetson GPU memory;
- Jetson power draw;
- thermal throttling;
- camera-to-output end-to-end latency under target deployment conditions.

These are explicitly marked `NOT_MEASURED`.

## 4.8 Acceptance test for future Jetson validation

The first hardware validation should run:

- batch = 1;
- fixed image resolution;
- warm-up before timing;
- at least 200 timed frames;
- p50/p95/p99 latency;
- steady-state power mode = 15 W;
- no display rendering in the timed loop;
- camera capture and inference measured separately and end-to-end.

The release gate is:

`p95 end-to-end latency <= 66.67 ms`

while maintaining the previously evaluated geometry/pose quality.

## 4.9 AI tool usage

AI assistance was used for implementation planning, code generation, interface review,
and documentation. Benchmark values were not generated by AI. The absence of Jetson
hardware is explicitly reported rather than filled with an estimated number.
